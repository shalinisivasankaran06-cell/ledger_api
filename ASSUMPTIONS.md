# Assumptions

The brief leaves some details open. These are the choices made, and why.

1. **Single currency, 2 decimal places.** No currency field; all amounts are in one currency
   with paise/cents precision. Stored as `NUMERIC(18,2)`, handled as `Decimal` (never float).
   Amounts with more than 2 decimal places are rejected (not rounded) so nothing is silently changed.
2. **Money in JSON is a string** (`"100.50"`) in responses, to avoid float precision loss in
   clients. Requests accept a number or a string.
3. **IDs are UUIDs (v4)**, generated by the server. They are unique without coordination
   and don't reveal how many accounts exist. A well-formed but unknown id → `404`;
   a value that is not a UUID → `422`.
4. **Insufficient balance returns `400 Bad Request`** with code `INSUFFICIENT_BALANCE`.
   (`422` would also be defensible; `400` was chosen to separate business-rule rejections
   from malformed input, which is always `422`.)
5. **Duplicate `reference_id` returns `409 Conflict`** with the already-stored transaction in
   `error.details.existing_transaction`, so a client retrying a request can see what was saved.
   This applies even if the retried request has a different amount or type: the
   `reference_id` identifies the transaction.
6. **Rejected transactions are not stored.** A debit refused for insufficient balance leaves no
   row, so its `reference_id` can be used again later.
7. **Sending `balance` (or `id`, `created_at`, or any unknown field) is a `422` error**, not
   silently ignored, to make it explicit that the client cannot set them.
8. **`name`** is required, trimmed, 1–100 characters. Names need not be unique.
9. **`description` is optional** (max 255 chars). The brief lists it as a field but does not
   list it among the required validations.
10. **`reference_id`** is required, trimmed, 1–100 characters, case-sensitive.
11. **`type` must be exactly `credit` or `debit`** (lowercase).
12. **Pagination:** `page` default 1, `limit` default 10, maximum 100 (configurable).
    Invalid values (0, negative, non-integer, above max) → `400 INVALID_PAGINATION`.
    A page beyond the last returns an empty list with the correct totals.
    `total_pages` is 0 when there are no records.
13. **Sorting:** newest first by `created_at`, with `id` as a tie-breaker so pages are stable.
    Timestamps are UTC (`TIMESTAMPTZ`).
14. **Overdrafts are never allowed.** Balance can reach exactly 0 but never below
    (also enforced by `CHECK (balance >= 0)`).
15. **Transfers** require both accounts to exist and be different; they use the client's
    `reference_id` on both the debit and the credit leg (allowed because uniqueness is per
    account) and link the legs with a shared `transfer_id`. A transfer is rejected as a
    duplicate if either account already has that `reference_id`.
16. **No authentication/authorisation.** Not requested; in production every endpoint would
    sit behind auth, and accounts would belong to users.
17. **Accounts cannot be deleted or renamed** through the API (not requested; deleting an
    account with history would break the ledger).
18. **Extra endpoints** beyond the brief: `GET /accounts/{id}` (account details) and
    `GET /health`.
19. **Database: PostgreSQL**, because the requirements (atomic transactions, row-level locks,
    CHECK/UNIQUE constraints) are exactly what a relational database guarantees.
